# Free Domain Name registry

This repository is the public, PR-governed source of truth for names in the Free
Domain Name resolver. The browser extension reads a generated client index;
humans review one small JSON file per name.

The registry may override **any** domain, including real domains such as
`google.com`. That is intentional. When public DNS also answers, the extension
shows a conflict screen and the user chooses which destination to open.

## Sharded source layout

Records are not kept in one `registry.json`. Each name has its own file:

```text
names/
  goo/gle/google.com.json
  hel/lof/hello.fdn.json
  doc/sfd/docs.fdn.json
  dem/ofd/_wildcard.demo.fdn.json
  ins/ecu/insecure.fdn.json
  abc/fdn/abc.fdn.json
  xyz/fdn/xyz.fdn.json
  ipm/api/ipmap.info.json
```

The shard path is deterministic. Dots are removed from the name, then the first
three characters become the first directory and the next three the second:

| Name | Path |
| --- | --- |
| `google.com` | `names/goo/gle/google.com.json` |
| `abc.com` | `names/abc/com/abc.com.json` |
| `*.demo.fdn` | `names/dem/ofd/_wildcard.demo.fdn.json` |
| `a.com` | `names/aco/m__/a.com.json` |

The full name remains in the filename and in the record, so a path is
self-describing. A wildcard file starts with `_wildcard.` because `*` is not a
portable filename character. Exact names may not start with `_` under the
validator, so the two cannot collide.

`registry.json` is only the manifest (schema/layout/counts). `client.json` is
generated by `node scripts/build-client.mjs`; never hand-edit it.

## Record format

One record per file:

```json
{
  "name": "insecure.fdn",
  "url": "http://203.0.113.10:8080/",
  "a": ["203.0.113.10"],
  "owner": "free-domain-name",
  "description": "HTTP/IP-only demo with a non-default port. TEST-NET-3 is not reachable.",
  "updatedAt": "2026-11-10T21:30:00Z"
}
```

- `name`: exact hostname or one leading wildcard. At least one dot is required.
  `*.com` is rejected because it would claim a whole TLD.
- `url`: HTTP(S) target, including an optional port. This is what the browser
  opens. **Ports are first-class.** `abc.fdn -> 203.0.113.10:80` and
  `xyz.fdn -> 203.0.113.10:8080` are different names and are allowed.
- `cname`: hostname target; the extension opens `https://<cname>/`.
- `a` / `aaaa`: DNS metadata. If no URL/CNAME exists, the first address is used
  as an HTTP target.
- `owner`: GitHub handle accountable for the record.
- `description`: optional, max 280 characters.
- `updatedAt`: optional ISO date.

Constraints: unique names; deterministic shard path; no mid-name wildcards; no
URL credentials; no non-HTTP(S) schemes; no target that this same registry
intercepts (loops). The generated client is capped at **2,000 records** because a
browser cannot install an unbounded number of declarative rules.

## Collisions and overwriting

A name maps to exactly one path. Two files with the same normalized name are
rejected by `scripts/validate.mjs`; the CI also verifies every file lives at the
path derived from `record.name`. A PR cannot add a second `abc.com` and silently
win — the duplicate fails CI.

Changing an existing record is still an explicit GitHub PR that edits that one
file. Protect `main`, require review, and treat an owner change as a security
change. The validator cannot know whether a PR author is the owner; GitHub review
is the authorization boundary.

Two names may share an IP or a port. Only the name must be unique.

## Sample records

- `google.com` -> `http://example.com/`: real-domain conflict demo. **Remove this
  before a production registry.**
- `hello.fdn`, `docs.fdn`: ordinary records.
- `*.demo.fdn`: wildcard.
- `insecure.fdn` -> `http://203.0.113.10:8080/`: HTTP/IP warning and port demo.
- `abc.fdn` -> `http://203.0.113.10/` and `xyz.fdn` ->
  `http://203.0.113.10:8080/`: same IP, different ports; both allowed.
- `ipmap.info` -> `http://ipmap.vitrn.com/`: a normal hostname target.

## Adding a name

1. Fork this repository.
2. Compute the path with `node -e "import('./scripts/shard.mjs').then(m => console.log(m.recordPath('your.name')))"`.
3. Add `names/<first3>/<next3>/<name>.json` with one record object.
4. Update `recordCount` / `wildcardCount` and `updatedAt` in `registry.json`.
5. Run `node scripts/build-client.mjs` and commit the regenerated `client.json`.
6. Open a Pull Request. CI runs `validate.mjs`, the client freshness check, and
   AJV schema validation.
7. A maintainer reviews ownership, target safety, and accuracy.

By opening a PR you confirm you control the target and accept that maintainers may
remove records for abuse, phishing, malware, or trademark issues.

## Scale note

The 3/3 tree avoids one enormous directory and is review-friendly: the theoretical
first-level space is 46,656 buckets and the second level is 46,656 more. That does
**not** make GitHub a 5-billion-file database, and a browser extension cannot
install 5 billion DNR rules. For that scale you need a database/object store and a
local resolver/proxy that looks names up on demand. The sharded tree is the
correct source layout; the generated client is the bounded v1 bridge.

## Local validation

```bash
node scripts/validate.mjs
node scripts/build-client.mjs --check
npx --yes -p ajv-cli@5 -p ajv-formats ajv validate -c ajv-formats \
  -s schema.json -d client.json --spec=draft2020 --strict=false
```

From the extension checkout, the stricter runtime validator is:

```bash
npx tsx scripts/validate-registry.ts /path/to/client.json
```
